# DIA-017 — RuleSet: the rules a game is played under
**Spec:** §1 #4, §3.1, §4.1, §4.4, §11.4, §16.1, §17, §19.2
**Sequencing note:** post-M1 by default. M1 hardcodes fastpitch 12U and nothing in "score a half-inning
of one game" needs a second ruleset. It becomes urgent the first time two teams disagree about D3K.
**Goal:** give the app the config object the spec has referenced in nine places and the code has never
had — the *rules* a game is played under, distinct from the *park* it is played in.

## What exists, and what doesn't

**`FieldProfile` is built** (`app/lib/src/field/field_profile.dart`, §16.1): sport, fence poles,
`basePath`, `pitchingDistance`, `backstop`. One preset — `fastpitch12U`, 190/200/210 fence, 60 ft
bases, 40 ft rubber, its own comment flagging **⚠ draft values**. Its header already scopes the profile
*library* and per-game overrides to M2. **This ticket does not rebuild it**, and does not absorb it.

**`RuleSet` does not exist at all.** The spec names it in nine places; the code has two narrow
placeholders standing in for it — `BallKind.softball` in `call_screen.dart`, and a comment in
`zone_canvas.dart` saying so outright. Everything else is hardcoded:

| rule | where it is pinned today |
| --- | --- |
| dropped third strike is live | `GameState.uncaughtThirdStrikeLive` — always on, gated only on first base and outs |
| illegal pitch is a ball | `pitch_count_effect.dart` — comment says "softball", no gate |
| infield fly | `How.INFIELD_FLY` exists in the schema; **nothing in the app ever gates or offers it** |
| zone and batter's-box dimensions | §3.1 and §11.4 both say "a `RuleSet` concern"; canvas hardcodes |
| courtesy runners, DP/Flex, run rules, substitution validation | not built |

## What M1 ships always-on, for this ticket to gate (2026-09-02)

The pattern Mark set for `slap`: build it always-on for M1, gate it here.

**The test for what belongs in this table (Mark, 2026-09-03): a `RuleSet` encodes rule *differences*,
not enforcement patterns.** Look-back and leaving early were listed here and have been removed — they
are rules *at every level*. Whether a given crew calls them varies by level and by crew, and the app
cannot know which umpire is working the plate, so it can never gate on that. The option has to exist
everywhere and the scorer records what was called. They are DIA-019 slice H's job — **building** them,
which this ticket's own 017c already said is the real work.

That correction matters beyond those two rules, because the reasoning that put them here was
*frequency*, and frequency is an argument about what to build **first**, never about what to make
available. A rule that is called twice a season still has to be enterable the twice it happens.

- **Illegal pitch** — the only one where the fallback is honest: it "could just be scored a ball,"
  which is what the count effect already does. `RunnerAdvanceReason.ILLEGAL_PITCH` and
  `CallType.ILLEGAL_PITCH_RULING` remain unreachable, and that is a deferral rather than a gate.
- **Balk** — deleted in v0.55 with baseball. If baseball ever returns it comes back with the ruleset
  that needs it.

The wider point for this ticket: an unwritten enum value is not automatically a gap. Three kinds —
**a real gap** (`BATTED_BALL_CONTACT`: has a §14 fixture, no UI path), **covered by a better path**
(`AWARDED`, superseded by the error link, deleted in DIA-019 slice L), and **waiting on a ruleset**
(the four above). Recording which is which stops the audit being re-run to the same conclusions — this
ticket had already logged infield fly before a fresh audit rediscovered it from scratch.

## Three axes, not two (Mark, 2026-08-28)

**Level** (10U, 12U, 14U, HS, …), and **the ruleset actually in
force**. The spec already separates the first and last — `GameStart` carries *"teams, rosters,
**RuleSet, FieldProfile**"* as distinct fields — and §19.2 already says how level fits: *"Age group +
sport selects the builtin `FieldProfile` preset and `RuleSet`."*

**Selects**, not *is*. That distinction is the whole design, and Mark's case is what forces it:

> *"The same age, say 10U, will play D3K in some tournaments and not in others. You can see the same
> thing with infield fly."*

So level cannot *be* a ruleset. If 10U → rules were a fixed mapping, "10U but with D3K" would be
unrepresentable, and it is a real Saturday. Level **supplies defaults**; the game holds the answer.

**The consequence is that `RuleSet` is a record of individual switches, not a sealed preset.** Named
presets ("10U", "HS fastpitch") are shorthand for *setting several switches at once* — the same
relationship as the defensive-positioning presets in
[[defensive-positioning-is-its-own-state]], where "Infield In" sets four fielders and is not itself a
position. A preset the scorer cannot open and disagree with is a preset that will be wrong on a
Saturday and unfixable.

Mark, closing it: *"Maybe none of that matters though, because no one is forcing you to check those
boxes even if they are there."* Right — variation stops being a modelling problem the moment defaults
are only defaults.

**One caution that follows.** A wrong default is *silently* wrong. If D3K defaults on and this
tournament does not play it, the loop offers a resolution that should not exist and the scorer may
take it — the same shape as `BatterOutcome.atBat` defaulting to `true` and hiding four bugs (DIA-015).
So defaults must be the genuinely common case, and the values in force need to be **visible before the
first pitch**, not buried in settings.

## Also worth deciding here

**Level is not only for rules.** It is the natural source of a `FieldProfile`'s defaults too — 12U
means 60 ft bases and a 40 ft rubber before anyone measures a fence. That is §19.2's *"the new coach
never sees a fence-distance form"*. So level feeds both, and neither owns it.

**The park and the rules vary independently**, which is why they must not merge: two teams can play
12U rules on differently-sized parks, and a tournament can play 14U rules on a 12U field. Merging them
forces one of the two to lie.

## Proposed slicing

- **017a — the type and its defaults.** `RuleSet` as switches, the level concept, builtin presets per
  sport × level, and `GameStart` carrying it. No behavior change: every switch defaults to what the
  code hardcodes today, so the suite proves the refactor is neutral before anything reads it.
- **017b — the M1 rules read it.** `uncaughtThirdStrikeLive` consults D3K; illegal pitch consults the
  sport. These are the two already-shipped behaviors that are silently sport-specific.

  **`slap` (Mark, 2026-08-28; revised v0.55).** DIA-014b shipped Bunt · Slap · Slash ungated, on the
  reasoning that a running slap is fastpitch's and the other sport should not be offered it. **That
  reason is gone** — there is no other sport as of v0.55, so slap needs no gate today. It stays in
  this table because a *level or association* could still want it off, which is the axis that
  survived. The hook remains in `_batterActions` in `outcome_step.dart`.
- **017c — ~~the rules that exist only in the schema~~.** Moved to DIA-019 slice H (2026-09-03). This
  slice was right that "gating them is also *building* them" and then filed the work here anyway.
  Infield fly, look-back and leaving early are rules at every level, so there is nothing here to gate;
  they need a way in, not a switch.
- **A settings surface** is out of scope and is the real dependency for any of this being usable —
  §19.4's navigation does not exist yet.

## Out of scope

`FieldProfile`'s library and per-game overrides (M2, §16.1's resolution order). The batter-height
inputs behind §3.1's zone dimensions. Anything that needs a roster.

## Spec protocol

§4.4's `GameStart` already lists `RuleSet`, so nothing there changes. If the switch list is written
down — and it should be — it wants a section of its own rather than nine scattered mentions, which
means the three-place protocol plus the two `CLAUDE.md` refs.
