# DIA-012 — Theme plumbing: brand baseline + swappable accent context (placeholder)

**Spec:** §23.1–23.3 (design language, semantic reservations, color contexts) (v0.37)

**Sequencing note:** despite its ID, this lands **before or alongside DIA-007**, not after DIA-011.
DIA-007 is the first ticket that builds real in-game UI, and every widget it writes will read colors
from somewhere. If that somewhere is a hardcoded `Color(0xFF…)` literal, DIA-007's whole surface has
to be reworked when real theming arrives. This ticket exists so the game UI is written theme-aware
from its first commit — it is deliberately *plumbing only*, not a theming feature.

**Goal:** stand up a single source of truth for app color, consumed via `Theme.of(context)`, with a
brand baseline that never changes and one accent slot that swaps by context. Placeholder values
throughout — no picker UI, no real palette, no persistence. Deliverable is the seam, not the paint.

## The model (three tiers, one accent)

- **Brand baseline — always, never overridden.** Surfaces, backgrounds, nav chrome, app bar, logo
  lockup, splash, onboarding, typography scale, and the **semantic reservations** (§23.2):
  amber = uncertainty (count HUD, §12.5), amber = misplay (§13, §15.3), red = error states. These
  are load-bearing meaning, not decoration; nothing in tiers 2–3 may touch them.
- **Accent — exactly one slot** (§23.1.2: "one accent system"). Filled by:
  - **Own team** (default, everywhere after onboarding) — the user's team primary.
  - **Opponent** (contextual) — that opponent's single main color, swapped in while the user is
    inside that opponent's space.
- **Own-team secondary color** is captured in the model but is **not a second accent.** Its only
  sanctioned use is a secondary series in own-team charts. If it starts appearing as a second
  highlight color, that's a §23.1.2 violation — stop and re-propose.

## Where the swap happens (and where it doesn't)

Opponent context is a *drill-in* state, not a game state — being mid-game is irrelevant to it:

- **Swaps:** opponent detail / scouting report (§18.1 hitter card + full-screen detail), the
  due-batter deck when scoped to that opponent (§18.2), live game against them, their book history.
- **Does not swap:** schedule and any list/index screen showing multiple opponents, own-team stats
  and roster, settings, onboarding. Multiple accents fighting in one list is noise, not information
  (§23.1.1), and it destroys the signal by making it constant.
- Rule of thumb: **baseline accent = browsing, opponent accent = focused on one team.**

## Design constraints

- **§23.3 is the contract; this ticket is its plumbing.** Where this ticket and §23 disagree, §23
  wins — flag it rather than implementing the ticket's version.
- **Colors are data, themes are derived.** Store a hex string on the team/opponent record; never
  store a `ThemeData` or a baked palette. In M1 there is no team/opponent entity yet — use a stub
  provider returning hardcoded seeds (one own team, two named opponents) so the swap is exercisable.
  Wiring to real records is a later ticket and must not require touching widget code.
- **Derivation is a pure function**, testable with no widget tree and no navigation:
  `deriveScheme(accentSeed, brandBaseline) → ColorScheme`. This is also the single future home for
  the contrast guardrail — one place to add it, not scattered at call sites.
- **Riverpod holds the current context** above `MaterialApp` (per CLAUDE.md stack); `ColorScheme` is
  derived reactively from it. Context is a value like `ColorContext.ownTeam` /
  `ColorContext.opponent(teamId)` — not a boolean, not a live-game flag.
- **Zero hardcoded color literals in UI code from this point forward.** Everything goes through
  `Theme.of(context)` / the scheme. Applies to DIA-007 and everything after it.
- **Dark mode is not optional** (§23.1.4, night games): every tier resolves in both light and dark.
  Placeholder palettes must include both, even if provisional, or DIA-007 will only be correct in one.
- Arbitrary accent seeds will eventually collide with the reserved semantic amber/red (a team whose
  color *is* orange) — Open Question #10. Not solved here, but the derive function is where it gets
  solved, so don't design it in a way that forecloses that.

**Accept:**

- Unit tests: `deriveScheme` is pure and deterministic; identical seeds produce identical schemes;
  brand-baseline tokens (surface, chrome, semantic amber/red) are byte-identical across own-team and
  opponent contexts, and only accent tokens differ. Both brightness modes covered.
- Widget tests: default context resolves to own-team accent; switching to an opponent context changes
  accent tokens app-wide without altering brand chrome; switching back restores exactly.
- A repo check (test or CI grep) failing on raw `Color(0x…)` / `Colors.*` literals in `app/lib/src/ui/`,
  with a documented allowlist for the brand baseline definition itself.
- DIA-007's widgets, when built, read every color from the theme. (Cross-ticket; note it in DIA-007's PR.)

**Out of scope:** the real Diamond palette (blocked on the logo/brand work — placeholder values here
are explicitly throwaway); team/opponent color picker UI; persistence and the team/opponent data
model; contrast-check fallback and the non-color context signal §23.1.7 requires (a persistent
"Scouting: <team>" label — worth doing, later ticket); `AnimatedTheme` crossfade on context switch
(§23.1.6 permits it as state-change motion, but it's polish); heat-map colormaps (§18.3) and any
chart color logic.
