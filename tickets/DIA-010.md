# DIA-010 — Scoring overrides: EarnedRunOverride + RbiOverride
**Spec:** §13.1, §13.3, §13.5
**Sequencing note:** in M1 but doesn't gate DIA-009 — the acceptance script doesn't exercise an
override. Fine to land before or after DIA-009; work in ID order only if Mark hasn't said otherwise.
**Goal:** implement the §13.5 narrow exception — let the scorer directly override the derived
earned/unearned ruling and RBI credit for one specific scored run, for the judgment calls
§13.3's automatic reconstruction can't reach. Schema for both events already lands in the
same commit as the §13.5 spec amendment (v0.17); this ticket is the schema codegen +
projection wiring + UI entry point.
**Design constraints:**
- Both events anchor to a `RunnerAdvance{to: 4}` event id (`runEventId`) — one run at a time,
  never a batter's whole line or a box-score total. See §13.5 for why per-run, not per-batter.
- Reuse the standard `corrects`/`VoidEvent` mechanism for flipping or clearing an override —
  no bespoke "latest wins" field or a separate clear-override event type.
- `earned_runs.dart`'s `reconstructEarnedRuns` (DIA-004) takes the override map as an input
  and prefers it per `runEventId`, falling through to the existing derivation when absent.
  RBI credit in `official_scoring.dart`'s `BatterOutcome.rbi` gets the equivalent treatment.
- Event inspector surfaces "overridden by scorer" + the optional `note`, same visual pattern
  DIA-004 already uses for §13.2 error attribution.
**Accept:** unit tests: an override flips a fixture-04-shaped scenario's earned ruling both
directions; a voided override reverts to derivation; an `RbiOverride` changes RBI credit
without touching other runners' lines on the same play. No change to the six §14 fixtures'
expected output (none of them uses an override).
**Out of scope:** any UI beyond a functional entry point (long-press/edit affordance can be a
stub); bulk/box-score-level editing (see §13.5's "not a general-purpose editor" — if this
becomes a common need, that's a signal the derivation is wrong, not that the override
surface should grow).

# Proposal (Claude, 2026-08-27) — read before starting

Researched against the code as it stands on `main` today. **Three of this ticket's premises have
expired**, and one of them changes the ticket's shape.

## 1. The schema does not exist

The ticket says *"Schema for both events already lands in the same commit as the §13.5 spec amendment
(v0.17)"*. It didn't. `schema/events/` holds eleven files and neither override is among them; there is
no `EarnedRunOverride` or `RbiOverride` in the generated Dart either.

So **DIA-010 owns the schema**, which makes it a §21.5 atomic commit — edit schema → regenerate Dart
and TS → update fixtures and tests, one commit. That is not extra risk, it is just a different first
step than the ticket describes. `count_correction.schema.json` is the precedent to copy from: it is
the §12.5 override this ticket's §13.5 pattern was explicitly modelled on.

## 2. There is no event inspector to surface anything in

Accept says the *"event inspector surfaces 'overridden by scorer' + the optional `note`, same visual
pattern DIA-004 already uses."* There is no inspector in `app/lib/src/ui/` — the closest surface that
exists is `play_chain_strip.dart`, which shows a play's chain rather than a run's ruling.

**Recommendation: drop it from Accept rather than build one here.** An inspector is its own design
problem — it is the "explainable" half of §13.1, and it wants to explain *every* derived ruling, not
just overrides. Building a one-off surface for two event types would be the thing §13.5 warns against
one level up. The `note` field still gets written and still round-trips; it simply has no reader yet,
which should be *stated* in the ticket rather than left as a silently unmet criterion.

## 3. The RBI half should follow DIA-015, not lead it

This is the sequencing finding and the reason to read this before scheduling.

RBI credit lives in `official_scoring.dart`'s `_batterOutcome` (`var rbi = 0`, line ~790). **DIA-015
Part 1 restructures that entire function** — from per-batter to per-plate-appearance, resolving
`sacrifice` above the branching, computing `atBat` explicitly on every path. Hooking an override into
the current shape means writing that hook twice.

The earned-run half has no such conflict: `reconstructEarnedRuns` is a separate function DIA-015 does
not touch.

**So: `EarnedRunOverride` can go whenever. `RbiOverride` should wait for DIA-015 Part 1.** They are
separable — same pattern, different consumers — and splitting them costs nothing because the schema
work for both lands in one commit regardless.

## 4. One design change I would make

The ticket says `reconstructEarnedRuns` *"takes the override map as an input"*. I would **derive it
inside the function from the event stream instead**, and not add a parameter.

Overrides *are* events. Its signature is already
`reconstructEarnedRuns(List<GameEvent> visibleLogicalOrder, {startingFrom, scoring})` — the stream is
right there, and the same fold that finds the advances can pick up the overrides anchored to them. A
map parameter would let a caller pass overrides that disagree with the stream they were computed
from, which is a class of bug that cannot occur if the function reads one source. It also means no
call site changes.

"Latest visible override wins" then falls out of the existing machinery rather than needing rules of
its own: `visibleLogicalOrder` has already dropped voided events, so the last override for a
`runEventId` in that list is the live one.

## Proposed slicing

- **010a — schema + earned runs.** Both schemas (one atomic commit), `reconstructEarnedRuns` reading
  overrides off the stream, unit tests both directions, plus a voided-override-reverts-to-derivation
  test. Independent of everything.
- **010b — RBI.** After DIA-015 Part 1. The equivalent treatment in whatever `_batterOutcome` has
  become, plus the multi-run test Accept already names: one run's credit corrected without disturbing
  the others on the same play.
- **Entry point:** its natural home is a box score, which **DIA-009** builds. Until then a functional
  stub has nowhere real to live, and Accept already scopes UI out. Worth landing 010a/010b as pure
  projection work and letting DIA-009 or a later UI ticket attach the affordance.

## What I would not change

The per-run anchoring, the `corrects`/`VoidEvent` reuse, and the refusal to build a general-purpose
editor are all right and all still hold. §13.5's own closing line is the test to keep applying: a
projection that needs routine hand-correction means the derivation is wrong, and the override is not
the place to hide that.
