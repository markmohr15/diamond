# DIA-010 — Scoring overrides: EarnedRunOverride + RbiOverride
**Spec:** §13.1, §13.3, §13.5
**Sequencing note:** in M1 but doesn't gate DIA-009 — the acceptance script doesn't exercise an
override. Fine to land before or after DIA-009; work in ID order only if Mark hasn't said otherwise.
**Goal:** implement the §13.5 narrow exception — let the scorer directly override the derived
earned/unearned ruling and RBI credit for one specific scored run, for the judgment calls
§13.3's automatic reconstruction can't reach. Schema for both events already lands in the
same commit as the §13.5 spec amendment (v0.17); this ticket is the schema codegen +
projection wiring + UI entry point.
**Design constraints:**
- Both events anchor to a `RunnerAdvance{to: 4}` event id (`runEventId`) — one run at a time,
  never a batter's whole line or a box-score total. See §13.5 for why per-run, not per-batter.
- Reuse the standard `corrects`/`VoidEvent` mechanism for flipping or clearing an override —
  no bespoke "latest wins" field or a separate clear-override event type.
- `earned_runs.dart`'s `reconstructEarnedRuns` (DIA-004) takes the override map as an input
  and prefers it per `runEventId`, falling through to the existing derivation when absent.
  RBI credit in `official_scoring.dart`'s `BatterOutcome.rbi` gets the equivalent treatment.
- Event inspector surfaces "overridden by scorer" + the optional `note`, same visual pattern
  DIA-004 already uses for §13.2 error attribution.
**Accept:** unit tests: an override flips a fixture-04-shaped scenario's earned ruling both
directions; a voided override reverts to derivation; an `RbiOverride` changes RBI credit
without touching other runners' lines on the same play. No change to the six §14 fixtures'
expected output (none of them uses an override).
**Out of scope:** any UI beyond a functional entry point (long-press/edit affordance can be a
stub); bulk/box-score-level editing (see §13.5's "not a general-purpose editor" — if this
becomes a common need, that's a signal the derivation is wrong, not that the override
surface should grow).
