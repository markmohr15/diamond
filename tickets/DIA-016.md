# DIA-016 — Design foundations: the real palette, typography, and component definitions
**Spec:** §18.7 (design language), §23.1–23.3 (color contexts, semantic reservations)
**Sequencing note:** M1-adjacent. Gates the design half of **DIA-014** and any later screen work —
every surface currently renders on Flutter defaults with placeholder color. Does **not** gate
DIA-009; the acceptance script cares about behavior, not paint.
**Goal:** replace DIA-012's placeholders with Diamond's actual brand, add the typography that has
never existed, and define the component vocabulary — button, modal, chip, card, spacing, radii — that
screens are currently inventing one call site at a time.

## What already exists, and what doesn't

**DIA-012 built the seam and said so:** *"Every color in this file is a placeholder and is expected to
be thrown away. What is not provisional is the seam."* `brand_baseline.dart` is the only file in
`app/lib/src/ui/` permitted to hold color literals — enforced by `no_color_literals_test.dart` — and
every widget already reads `Theme.of(context)`. `DiamondSemantics` exists as a `ThemeExtension` with
slots for uncertainty, misplay, and callable. **None of that needs rebuilding.**

**Typography does not exist at all.** No `TextTheme`, no font family, nothing — every surface is on
Flutter's defaults. This is a real difference from color, where the pipe is built and only the values
are provisional.

**Component definitions do not exist.** The symptom is `field_dialog.dart`, which hand-scales its own
chip, button, and list-tile themes at a single call site because there was nothing shared to reach
for. Every popup on the field surface inherits from that one function by accident of history.

## The brand: 1A "Infield"

From Claude Design's `Diamond Branding.dc.html`. **1A is the build direction; 1B ("Night Game") is
reference only and is not being used.**

| token | hex | role |
|---|---|---|
| Grass | `#2E5E3E` | primary accent |
| Clay | `#B4643C` | secondary accent |
| Ink | `#16211C` | type, chrome, borders |
| Chalk | `#F4F2EB` | surface |

Supporting neutrals used throughout the panels: `#FFFEF9` (raised panel), `#E7E5DE` (page ground),
`#D6D3C8` (hairline), `#4A4A44` (secondary type), `#8A8A80`/`#7A7A70` (muted labels).

**Typography: Space Grotesk (400/500/700) everywhere, JetBrains Mono (400/500/700) for counts, codes
and positions** — anything numeric. The brand note gives the reason and it is a real constraint, not
a preference: *"two faces with the same squared skeleton, so the app reads as one system."*

**The mark** is a chalk-line diamond — one stroke weight, one angle, a 45°-rotated square outline in
Grass with home plate anchoring the bottom in Ink. Wordmark in Space Grotesk 700 at `-0.045em`. App
icon: 88px, 20px radius, Grass ground, Chalk diamond, Clay plate. Tagline **"Coach the whole field."**

## Two things to resolve before writing code

**1. Clay collides with the semantic reservations, and §23.2 outranks it.** The palette has *no amber
and no red* — but §23.2 reserves amber for uncertainty (the count HUD when a pitch makes the count
ambiguous, §12.5) and for misplay (chain nodes, §13/§15.3), and red for error states. Those are
load-bearing meaning, not decoration.

`#B4643C` is an orange-brown sitting close to the amber band. Panel 5A already uses Clay decoratively
— "→ STRIKEOUT" in the count-consequence subtitle — and the chain strip renders misplays amber. In
sunlight, on a tablet, a coach must be able to tell *"this is emphasis"* from *"this fielder muffed
it."* Decide one of: Clay is barred from any surface where amber carries meaning; or the amber values
move far enough from Clay to stay separable; or Clay is demoted from a UI accent to a brand-only
color (icon, card, dugout sign).

**2. The fonts must be bundled, not fetched.** The design pulls Space Grotesk and JetBrains Mono from
Google Fonts via `<link>`. **Offline-first is the prime directive** (§12.6, §19.1, §21.5): no feature
may require connectivity to record or view anything during a game, and a dugout has no signal.
Ship the font files in the app bundle and declare them in `pubspec.yaml`. A runtime fetch — including
the `google_fonts` package's default behavior — is a build failure waiting for a Saturday morning
with no bars.

## Deliverables

- **Palette** — 1A's four brand colors plus neutrals, and *deliberately chosen* amber and red for the
  §23.2 reservations, picked against Grass and Clay for daylight separability. All of it in
  `brand_baseline.dart`; `no_color_literals_test` must still pass.
- **Typography** — bundled fonts, a `TextTheme` scale, and a documented rule for when a number takes
  the mono face. Counts, codes, positions, and distances are mono; prose is not.
- **Components** — filled/outlined/text buttons, the centered modal (`field_dialog.dart`'s hand-rolled
  scaling folds into it), choice/filter/action chips, and the raised panel. Sized for a coach standing
  in a dugout with the sun on the screen, with a stated **minimum touch target**.
- **Spacing and radii tokens** — 5A and 4A use a consistent rhythm (28px panel padding, 16/12px radii,
  8px gaps) that is currently hardcoded per widget.
- **Elevation** — one shadow definition; 5A's sheet uses a heavy upward `0 -18px 44px`.
- **App icon and splash** from the mark.

## Accept

- Every screen renders in Space Grotesk/JetBrains Mono with **networking disabled**.
- `no_color_literals_test` passes; no new literal outside `brand_baseline.dart`.
- The amber reservations are visibly distinct from Clay — verified on device in daylight, not on a
  desk monitor, per §18.7's "sunlight-glanceable" bar.
- Goldens regenerated. **Note this will change every golden in the suite**, and the two field goldens
  already fail on CI for unrelated rasterization reasons — worth settling that first so a real
  regression is not hidden inside an expected mass update.
