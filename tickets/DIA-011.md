# DIA-011 — Pitch bounce capture: BounceCoord, dirt-band hinge, plate/batter canvas
**Spec:** §3.1 (v0.31), §3.3, §4.1, §11.1, §11.4 (v0.31), §18.7
**Goal:** extend DIA-005's zone canvas into the full two-plane pitch-location surface described in §11.4.
The frontal plane gains a foreshortened home-plate anchor (17″ edge up-screen toward the pitcher, point
down-screen toward the catcher), flanking batter's-box outlines — both boxes always rendered as a frame of
reference on either side of the plate, with only the box the current batter occupies filled per
`batterSide` — and a visually distinct dirt band below the derived ground line. A release inside the dirt
band hinges the canvas to a top-down plate/dirt plane (true-pentagon plate from directly above, depth bands
growing up-screen toward the pitcher, negative depth below the plate toward the catcher, both batter's boxes
+ catcher position, lateral axis kept in exact register with the frontal plane above it). A second tap in
that plane sets `PitchThrown.bounceLocation` (§3.3). Skipping the second tap plus the existing
skip-location affordance (§11.2) records "in the dirt, depth unknown." Schema: `BounceCoord` (§3.3) and
`PitchThrown.bounceLocation` (§4.1) land via the standard schema → codegen → fixtures protocol
(CLAUDE.md non-negotiables).

**This is a refactor-then-build ticket, not a pure addition.** DIA-005 shipped with the coordinate mapping
(`zoneCoordFromLocal`/`localFromZoneCoord`, the `zoneMinX`/`Max`/etc. constants, `_canvasAspectRatio`) and
the background (`_ZoneCanvasBackgroundPainter`/`_ZoneBorderPainter`) hardcoded — module-level constants
and inline-instantiated painters, not anything the widget takes as a parameter, and the gesture handler
(`_handleLongPressEnd`) has exactly one hardcoded commit path with no branch point for a second plane. The
DIA-005 design constraint asking for these to be swappable was never actually met by DIA-005 itself (it
predates that constraint). DIA-011's first phase is therefore a real refactor of `ZoneCanvas` — extracting
the coordinate mapping and background into parameters the widget takes, and giving the gesture handler a
branch point for the hinge — *before* any new bounce-capture behavior is built on top. Size the ticket
accordingly; this is not a thin extension of an already-flexible widget.

**Measured baseline (DIA-005 demo render, 2026-07-24).** Recorded so the geometry work has a known
starting point rather than an impression. Values in `ZoneCoord`; zone rect = 297 × 410 px:

| | DIA-005 render | broadcast K-zone reference | §11.4 target |
|---|---|---|---|
| Lateral registration (plate 17″ edge vs. zone width) | 303 vs. 297 px — exact ✓ | 247 vs. 244 px — exact | exact |
| Axis scale ratio (px-per-x ÷ px-per-y) | 0.363 | — | 0.354 ✓ (within 2.5%) |
| Plate on-screen depth ÷ width | **1.00** (plan view) | **0.17** | 0.215 (band 0.15–0.25) |
| Plate front edge at | **y = −1.24** | y = −0.71 | y = −0.646 (`y_ground`) |
| Top of dirt band | y = −0.60 | — | y = −0.646 |
| Canvas world coverage | 91″ × 28″ (3.3 : 1) | — | ≈ 68″ × 61″ (≈ 1.11 : 1) |

Read: registration and axis scaling are already right and should not be "fixed." Essentially the entire
apparent error — a zone rect that looks like it floats too high above an oversized plate — is the missing
foreshortening, which alone accounts for ~0.55 zone-heights of the 0.59 discrepancy. Correcting the plate
perspective and placing its front edge on `y_ground` closes the gap without moving the zone rect at all.

**Design constraints:**
- **The hinge is `ZoneCanvasIntent.actual` only — a call is never a bounce.** `intendedLocation` stays a
  `ZoneCoord`; a coach calls "bury it down" as a low/chase call zone (§10.1's `Bury-Down`), never a bounce
  depth, and §17.4 already treats intent as frontal and the bounce as the actual it's judged against. So
  only the actual-location step ever produces a `BounceCoord`: in call mode the frontal plane still renders
  the plate/dirt for orientation, but a release low in the dirt band just commits a low `ZoneCoord` and
  does **not** hinge. Gate the plane-swap branch behind `mode == actual`. (Provisional — whether a bounce
  can ever be *called* is still open per Mark; "no" for now.)
- Coordinate mapping and background must end up as swappable parameters, not hardcoded (see above); the
  hinge fires **on release only**, never on arm/press, so the existing arm-low-drag-up-to-correct grammar
  keeps working untouched; no tap-vs-drag duration heuristic — an omitted second gesture plus the
  skip-location affordance already covers "depth unknown."
- **`y_ground` is derived, not a constant to taste** (§3.1). Compute it from §3.1's canonical 12U inputs
  (15.5″ / 24.0″ → −0.6458) as a function of zone-bottom-height ÷ zone-height, so per-batter zone heights
  drop in later without a second geometry pass. Never hardcode the rounded −0.65: the 0.7% gap sits inside
  the geometry tests' own tolerance. The dirt band is defined as `y < y_ground` — the hinge trigger and the
  physical ground line are the same line, so there is no separate band-height constant to tune.
- **The axis scale ratio is per-profile for the same reason.** `8.5″ / zoneHeight` is 0.354 at 12U and
  0.425 at 10U. Not a constant; must not be one in code.
- **Plate foreshortening comes from a real projection, not a hand-applied ratio.** Build the pinhole ground
  projector (camera height `H`, distance `d` to the 17″ edge, azimuth 0) and draw plate, boxes, and catcher
  through it; the ratio then falls out as `H / (d − 17″)` — default `H` = 4 ft, `d` = 20 ft → **0.215** —
  rather than being imposed. `d − 17″` is the plate's near point, which is *closer* than the edge `d`
  measures to; `d + 17″` is the sign error to watch for. Anchoring the projector so ground at `u = d` maps
  to `y_ground` is what makes the plate-front-edge identity hold for free. Both parameters, not literals.
- **The two camera constraints are coupled; satisfying one does not satisfy the other.** Ratio band
  0.15–0.25 ⇒ `0.15 (d − 17″) ≤ H ≤ 0.25 (d − 17″)`, which at `H` = 4 ft means **d ∈ [17.4 ft, 28.1 ft]**;
  splay ≤ 5% ⇒ d ≥ 14.9 ft. The ratio band binds first at this camera height, so d = 15 ft is *not* a legal
  camera despite passing the splay rule — it renders at 0.294. (0.297 is the ratio at the splay minimum
  itself, d = 14.875 ft; a correct number on the wrong row.) Anything selecting a camera, including test
  fixtures, checks both.
- **Ground scenery extends above `y_ground`; the trigger does not** (§11.1, §11.4). Ground in front of the
  plate is farther away and projects higher, so drawn ground spans the ground line while the hinge trigger
  stays strictly `y < y_ground`. Ground is **bounded by contrast, not extent**: draw it to its natural
  extent — the region in front of the plate is where a bounced pitch lands, and it is dirt — and fade it
  with distance, reaching neutral before it sits behind the zone rect. Fade endpoints tune with the two
  fidelity treatments; there is no `y` cap. (The horizon at the default camera sits at y = +1.354, inside
  the canvas and above the zone rect; the fade reaches neutral well below it and no horizon is drawn.)
- **The trigger is not identified by looking like dirt.** The landmark is the plate's 17″ front edge, which
  by construction lies on the ground line, reinforced by the fade's own tonal step — not a drawn full-width
  rule, which reads as an arbitrary graphic; revisit when the hinge gives the boundary interaction weight.
  Everything drawn above the
  line renders behind the marker layer.
- **Do not invert the ground plane to a depth.** `u = k / (y_horizon − y)` recovers a distance from any tap
  on drawn ground, and it is tempting because it is *correct* — but the same pixel is also a legitimate
  airborne location (y = −0.40 is both ground 2.8 ft out and a pitch 5.9″ off the dirt at the plate), and
  the airborne reading is the common case. Taps above `y_ground` are airborne; bounce depth comes only
  through the hinge and the top-down plane.
- **Perspective stops at the zone.** Plate, dirt, batter's boxes, and catcher take perspective; the zone
  rect and call grid stay strictly orthographic (§11.4). Perspective on the grid would make §10.1 `bounds`
  cells unequal tap targets and break tap-equals-coordinate.
- **Lateral registration is exact, not decorative** (§11.4): `x = ±1` must align with the plate's 17″ edge
  in both planes. Note the perspective consequence — the plate's near corners project slightly wider than
  `x = ±1`; assert registration against the 17″ edge specifically, never the widest visible point.
- **Widen the lateral range to `x ∈ [−4.0, +4.0]`** (from the current ±1.62). The requirement is not
  reaching the chalk but **containing where the batter stands**: a pitch may be recorded anywhere on the
  canvas, including at her body, and the silhouette lays over part of it. A 12U stance puts her body centre
  ≈ 26–30″ off plate centre (x ≈ 3.1–3.5, spanning x ∈ [2.4, 4.3]). Widening is free in tap precision — the
  canvas is height-limited, so the zone's on-screen size is set by the vertical scale and lateral range only
  adds pixels beside it; what it spends is horizontal room competing with the call grid, hence ±4.0 rather
  than ±6.0. The rulebook's 6″ is measured to the chalk's **inner (plate-side) edge**, so at plate depth the
  line spans x ∈ [1.706, 2.059] — both edges on-canvas at this range, so the band reads as a line instead of
  clipping into a wedge.
- **Trim the top extent to `y = +1.5`** — half a zone height above the zone, ≈ 12″ over the letters. Higher
  carries no scouting or development information (a foot over the head and two inches over it are the same
  observation; §17.4 buckets both as uncompetitive-high), so those pitches stay recordable but land
  unresolved on the top edge. Shoulder height (y ≈ 1.31) stays resolved. Frees vertical room for the count
  HUD and outcome row.
- **Check which canvas dimension binds before claiming a frame change is free** (§11.4). Height-bound, zone
  px follows `panelHeight / verticalExtent` and lateral range is irrelevant; width-bound — the real
  side-by-side layout, where a width budget leaves a call column — zone px follows
  `panelWidth × 2 / lateralExtent` and vertical extent is irrelevant. So trimming the top is free here and
  widening is what costs. "Widening is free" is not a general truth.
- **Both batter's boxes are always present, in both planes.** They're the reference frame for location on
  either side of the plate regardless of who's up — never hidden or omitted on one side. `x` stays absolute
  (§3.1), so the canvas never mirrors coordinates. Box dimensions come from `RuleSet`, never an
  `if (softball)`: baseball 48″ × 72″, fastpitch 36″ × 84″, both 6″ off the plate (§11.4's table). M1 uses
  the fastpitch values.
- **Occupied-side treatment defers to the shadow-batter part of this ticket.** The geometry part renders
  chalk only — no `batterSide` fill. §11.4's "subtly filled from `batterSide`" is superseded by the batter
  silhouette, which is a better answer to the same question (which side is up, and where does she stand):
  one fixed 12U height for now, mocked, with height driven by sport and age level later. Both land together
  so the canvas never carries two competing occupied-side cues.
- **Draw the inner and front chalk lines; not the back or outer ones** (§11.4 v0.31). Inner and front are
  what a coach reads position against; back and outer carry no locating information and run off-frame at
  true scale. Chalk is clipped only by the box's own extent and the canvas edge — **not** at `y_ground`, and
  there is no scenery cap to clip against — and fades with the ground it is painted on. Chalk is **3″**
  wide, measured outward from the inner edge (above).
- **Expected visible extent at the default camera:** the inner line is laterally on-canvas from
  `u ≈ 0.426 d`, nearer than the box's own back line, so nothing clips laterally and the near end is bounded
  by the canvas bottom at `u ≈ 199.7″` instead. Visible run ≈ 80″ of an 84″ box, y ∈ [−1.05, −0.363],
  turning a corner into ≈ 25″ of the 36″ front line before leaving frame. A box receding out of view,
  frame-cut as in the reference K-zone. This is the expected render, not a shortfall to correct.
- **The ground plane is not isotropic with the frontal plane** — it's a perspective projection, and the two
  planes share only the lateral axis (§3.3). Nothing may derive a depth from where a tap landed in the
  frontal plane's dirt band; depth exists only in the top-down plane after the hinge. Put a comment at the
  mapping boundary saying so, because "helpfully" inferring one is an inviting mistake.
- **The top-down plane is isotropic and shares px-per-x with the frontal plane**, so the plate is literally
  the same width in both views — the strongest available cue that the planes register. *Corrected in spec
  v0.35:* those two constraints leave the depth range no freedom — px-per-x parity fixes px-per-inch and
  isotropy makes the shared rect fix the vertical inches, giving **61.2″ = 5.10 ft** at 12U, not the −1 ft…
  +5 ft (72″) this bullet originally quoted. Only the anchor is free; it splits at **−2.5 ft … +2.60 ft**,
  the aft extent fixed in inches (plate pentagon + 13″) since the plate is 17″ for every batter.
- **Move Cancel / skip-location out of the canvas.** They currently overlay the dirt band, i.e. the hinge
  trigger region — a live hit-target conflict, and worse after the hinge, where dirt is the whole canvas.
  They belong in a strip outside the drawing area, present in both planes.
- **§18.7 items carried into this ticket:** the grid renders dark, not light blue on white (it disappears in
  daylight); the accent belongs to the tap marker, not the zone border (§18.7.3).
- **Fidelity is genuinely open, not a call for this ticket to make** (§11.4): build both a richer
  (dimensional plate/dirt, textured chalk) and a restrained (flat, neutral background) rendering of the
  entry canvas behind the *same* coordinate mapping, and field-test both on a real tablet in daylight
  before either is picked. Acceptance includes producing both for comparison, not shipping one
  predetermined look. The geometry above is *not* part of that question — it applies identically to both.
- **The silhouette is paint, never a hit target.** It renders behind the marker layer and takes no pointer
  events. A pitch may be recorded anywhere on the canvas including at the batter's body, so a silhouette
  that swallowed taps would make the region it occupies uncapturable — the opposite of why the lateral range
  was widened to contain her.
- **Shadow batter: build it behind a debug flag, as a calibration instrument** (§11.4). Its job is to prove
  the zone rect spans knee-to-armpit at the derived ground line; that's a check no table can perform. Do not
  ship it on the entry canvas — a fixed silhouette is honest only for the height it was drawn at and will
  contradict the zone rect for a tall or short kid. If it survives to a review surface later, it gets driven
  from a batter-height parameter.
- ~~Depth bands shown in the top-down view (0–2 ft, 2–4 ft, 4 ft+, per §11.4)~~ *dropped in spec v0.35* —
  they assumed the un-achievable range above (4 ft+ is off-canvas at +2.60), and a continuous float deserves
  an axis rather than buckets. Replaced by a gridline every foot, sign spelled out ("2 ft back").
  `BounceCoord.depth` was already a continuous float and nothing is bucketed in storage either way.
- **Command classification (§17.4) is out of scope.** It's explicitly "entirely projection" per spec,
  consuming `bounceLocation` after the fact with its own tunable thresholds. This ticket only has to
  capture the coordinate faithfully — it does not compute executed / competitive-miss / uncompetitive
  buckets.
**Accept:**
- Schema/codegen: `BounceCoord` and `PitchThrown.bounceLocation` round-trip Dart + TS codegen; any
  fixture exercising a bounced pitch is updated accordingly. *(Added in the hinge part, spec v0.35:*
  `depth` *is optional — "in the dirt, depth unknown" had no encoding otherwise, since* `depth` *was
  required and* `PitchThrown` *carries no bounced flag.)*
- Geometry tests (numeric, not golden — these are assertions about the mapping, not about the look). Every
  assertion computes its expected value from §3.1's canonical inputs, never from a rounded figure in prose:
  axis scale ratio = `8.5″ / zoneHeight` **per profile** (0.354 at 12U, 0.425 at 10U), driven at at least
  two profiles so a hardcoded constant fails; `y_ground` computes to −0.6458 at 12U and moves correctly when
  the zone-height inputs change; plate on-screen depth ÷ width ∈ [0.15, 0.25], 0.215 at the default camera;
  plate front edge lands on `y_ground` asserted across *two* cameras, since this is an identity independent
  of `H` and `d` (§11.4) and a single-camera test would not catch a projection built the wrong way — use
  (4 ft, 20 ft) → 0.215 and (3 ft, 18 ft) → 0.181, both of which satisfy the ratio band *and* the splay
  rule (do not reach for d = 15 ft; it fails the ratio band); a camera-validity check rejects an out-of-band
  pair; near-corner splay ≤ 5%; lateral range reaches ±4.0 with both chalk edges (1.706 and 2.059) on-canvas
  at plate depth, so nothing clips laterally and the box's near end is bounded by the canvas bottom instead;
  drawn ground spans `y_ground` and is bounded by fade rather than a `y` cap; chalk renders inner + front
  only, the inner line running ≈ 80″ of the 84″ box to y ≈ −0.363 at the default camera;
  `x = ±1` maps to the plate's 17″ edge in **both** planes; top-down plane px-per-x equals the frontal
  plane's.
- Widget tests: both batter's-box chalk lines render in both planes regardless of `batterSide`; box
  dimensions come from `RuleSet` and change with the sport; the shadow batter occupies the correct box for
  both `batterSide: 'L'` and `'R'` (shadow-batter part); a release inside the dirt band hinges to the
  top-down plane; a second tap there commits
  `bounceLocation` with correct shared-`x`/`depth` math, including the sign convention (positive = toward
  the pitcher/bounced out front, negative = past the back edge); **regression** — arming inside the dirt
  band but dragging up and releasing in the zone commits a normal `actualLocation` and never hinges;
  omitting the second gesture and using skip-location records depth-unknown; Cancel and skip-location have
  no hit-target overlap with the dirt band in either plane; golden tests for both planes, both fidelity
  treatments, tablet + phone.
- Design review pass (§18.7) comparing both fidelity treatments on a real tablet before either ships.
**Out of scope:** command classification / execution-rate projection (§17.4 — its own future ticket);
per-batter real zone height (still a placeholder — but `y_ground` and the axis ratio must be expressed as
functions of it, not literals, so it drops in without a second geometry pass); shipping the shadow batter on
any surface; the continuous press-drag-through-the-hinge accelerator gesture floated alongside the tap
version (future enhancement, revisit if the tap version feels slow in practice); **a tolerance band above
`y_ground` that would also hinge** — §11.4 asked for the trigger boundary to be re-checked "when the hinge
lands, since that is when the boundary starts carrying interaction weight", and that re-check happened on
device (2026-07-26): the boundary works, and the plate is a reliable target for it since the plate lies
entirely below `y_ground` by construction (front edge on the line, point 0.152 zone-heights under it).
Deferred past M1 rather than solved, because the trade is real: above `y_ground` a pitch can still be
genuinely airborne — a ball an inch off the dirt is a low pitch, not a bounce — so any tolerance buys a
more forgiving target at the cost of silently recording low pitches as bounces. Settle it with tap data
from a real game, not from a chair; DIA-006/007's `CallZone`
grid snapping (unrelated system).
