# DIA-011 — Pitch bounce capture: BounceCoord, dirt-band hinge, plate/batter canvas
**Spec:** §3.3, §4.1, §11.1, §11.4 (v0.24)
**Goal:** extend DIA-005's zone canvas into the full two-plane pitch-location surface described in §11.4.
The frontal plane gains a home-plate anchor (drawn in perspective — 17″ edge up-screen toward the pitcher,
point down-screen toward the catcher), flanking batter's-box outlines — both boxes always rendered as a
frame of reference on either side of the plate, with only the box the current batter occupies filled per
`batterSide` — and a visually distinct dirt band between the low-pitch region and the plate. A release
inside the dirt band hinges the canvas to a top-down plate/dirt plane (true-pentagon plate from directly
above, depth bands growing up-screen toward the pitcher, negative depth below the plate toward the
catcher, both batter's boxes + catcher position, lateral axis kept in exact register with the frontal
plane above it). A second tap in that plane sets `PitchThrown.bounceLocation` (§3.3). Skipping the second
tap plus the existing skip-location affordance (§11.2) records "in the dirt, depth unknown." Schema:
`BounceCoord` (§3.3) and `PitchThrown.bounceLocation` (§4.1) land via the standard schema → codegen →
fixtures protocol (CLAUDE.md non-negotiables).
**This is a refactor-then-build ticket, not a pure addition.** DIA-005 shipped with the coordinate mapping
(`zoneCoordFromLocal`/`localFromZoneCoord`, the `zoneMinX`/`Max`/etc. constants, `_canvasAspectRatio`) and
the background (`_ZoneCanvasBackgroundPainter`/`_ZoneBorderPainter`) hardcoded — module-level constants
and inline-instantiated painters, not anything the widget takes as a parameter, and the gesture handler
(`_handleLongPressEnd`) has exactly one hardcoded commit path with no branch point for a second plane. The
DIA-005 design constraint asking for these to be swappable was never actually met by DIA-005 itself (it
predates that constraint). DIA-011's first phase is therefore a real refactor of `ZoneCanvas` — extracting
the coordinate mapping and background into parameters the widget takes, and giving the gesture handler a
branch point for the hinge — *before* any new bounce-capture behavior is built on top. Size the ticket
accordingly; this is not a thin extension of an already-flexible widget.
**Design constraints:**
- Coordinate mapping and background must end up as swappable parameters, not hardcoded (see above); the
  hinge fires **on release only**, never on arm/press, so the existing arm-low-drag-up-to-correct grammar
  keeps working untouched; no tap-vs-drag duration heuristic — an omitted second gesture plus the
  skip-location affordance already covers "depth unknown."
- **Lateral registration is exact, not decorative** (§11.4): `x = ±1` must align with the plate's 17″ edge
  in both planes — a pitch tapped at the zone's right edge must visibly sit over the plate's right edge
  rendered below it.
- **Both batter's boxes are always present, in both planes.** They're the reference frame for location on
  either side of the plate regardless of who's up — outlines for both, sides never hidden or omitted. Only
  the fill (which box is occupied) changes per `batterSide`; `x` itself stays absolute (§3.1), so the
  canvas never mirrors coordinates.
- **Fidelity is genuinely open, not a call for this ticket to make** (§11.4): build both a richer
  (dimensional plate/dirt, textured chalk) and a restrained (flat, neutral background) rendering of the
  entry canvas behind the *same* coordinate mapping, and field-test both on a real tablet in daylight
  before either is picked. Acceptance includes producing both for comparison, not shipping one
  predetermined look.
- Depth bands shown in the top-down view (0–2 ft, 2–4 ft, 4 ft+, per §11.4) are a labeling/rendering
  concern only — `BounceCoord.depth` itself stays a continuous float, nothing is bucketed in storage.
- **Command classification (§17.4) is out of scope.** It's explicitly "entirely projection" per spec,
  consuming `bounceLocation` after the fact with its own tunable thresholds. This ticket only has to
  capture the coordinate faithfully — it does not compute executed / competitive-miss / uncompetitive
  buckets.
**Accept:**
- Schema/codegen: `BounceCoord` and `PitchThrown.bounceLocation` round-trip Dart + TS codegen; any
  fixture exercising a bounced pitch is updated accordingly.
- Widget tests: both batter's-box outlines render in both planes regardless of `batterSide`; the occupied
  box fills correctly for both `batterSide: 'L'` and `'R'`; plate renders as the frontal-plane anchor with
  correct perspective proportions and exact lateral registration against the zone rect above it; a release
  inside the dirt band hinges to the top-down plane; a second tap there commits `bounceLocation` with
  correct shared-`x`/`depth` math, including the sign convention (positive = toward the pitcher/bounced
  out front, negative = past the back edge); **regression** — arming inside the dirt band but dragging up
  and releasing in the zone commits a normal `actualLocation` and never hinges; omitting the second
  gesture and using skip-location records depth-unknown; golden tests for both planes, both fidelity
  treatments, tablet + phone.
- Design review pass (§18.7) comparing both fidelity treatments on a real tablet before either ships.
**Out of scope:** command classification / execution-rate projection (§17.4 — its own future ticket);
per-batter real zone height (still a placeholder; unaffected since the dirt-band trigger is visual/layout
only, never a stored threshold); the continuous press-drag-through-the-hinge accelerator gesture floated
alongside the tap version (future enhancement, revisit if the tap version feels slow in practice);
DIA-006/007's `CallZone` grid snapping (unrelated system).
