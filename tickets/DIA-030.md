**Sequencing note:** **Not M1.** Tooling. Mark, 2026-11-24: a second app wants the latest Flutter,
and Diamond's pin (3.44.0) is six releases behind.
**Status:** 030a merged (#84): 22 goldens re-rendered on the runner at 3.44.0, 0 changed. 030b

## Why the upgrade starts with goldens

CI does not depend on a Docker image. `subosito/flutter-action` installs any released Flutter on
`ubuntu-latest`, so CI could run 3.50.1 today. The image only ever served `tools/goldens.sh`,
which rendered goldens locally in `ghcr.io/cirruslabs/flutter`. That publisher stopped at
**3.44.0**: on 2026-11-24, `3.50.0` and `3.50.1` returned 404, and its `stable` tag still held
3.44.0, last pushed 2026-05-20.

So the next bump has nowhere to regenerate goldens, and that comes first.

## Slices

**030a: regenerate goldens on CI's runner (Mark, 2026-11-24: option 1 over building our own
image).**

- `.github/workflows/goldens.yml` reruns the goldens with `--update-goldens` on the runner that
  compares them, and uploads only the changed and new PNGs.
- It runs when triggered (`tools/goldens-ci.sh [-n name]`, which waits and then unpacks the
  images), and by itself on any PR that changes the version file or the workflow.
- `.github/flutter-version` is now the single pin, read by CI, the goldens workflow and
  `goldens.sh`. Before, two files each named 3.44.0 and had to be bumped together.
- **Proof:** this PR changes the workflow, so the workflow runs on it. At 3.44.0 it must come back
  with **zero** changed goldens. Anything else means the runner renders differently from the
  committed images, and the approach is wrong.
- `workflow_dispatch` only becomes triggerable once the file is on `main`. Until 030a merges,
  `goldens-ci.sh` cannot run.

**030b: the bump.**

- Set `.github/flutter-version` to 3.50.1. The goldens arrive as the PR's artifact.
- Fix whatever `flutter analyze` and the tests raise; alchemist is the likeliest dependency to need
  a bump.
- Retire `tools/goldens.sh`.
- Pin Diamond in FVM (Mark, 2026-11-24): `.fvmrc` at the repo root, `.fvm/` ignored, and VS Code's
  `dart.flutterSdkPath` pointed at `.fvm/flutter_sdk`, so Diamond and Mark's other app each run
  their own Flutter.
